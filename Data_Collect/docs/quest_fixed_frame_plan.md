# Quest 手柄改用空间固定坐标系的方案

本文件是实施方案。本次没有修改 APK、遥操运动算法或现场配置，也没有下发机器人运动命令。

后续检索补充：[无需手持直线运动的替代方案](quest_fixed_frame_alternatives.md)。下文描述的是“输出追踪空间位姿”这一路线；它不是唯一方案。利用当前双手柄数据、将左手柄固定作参考，可以在 PC 构造固定参考位姿，不必先修改 APK。该适配尚未实测。

## 1. 当前位姿如何表示

采用记号 `T_AB` 表示“B 坐标系在 A 坐标系中的位姿”，它也将 B 中的点转换到 A。W 为 Quest 追踪空间，H 为头显，C 为手柄，B 为机器人基座。

Oculus Reader 上游 APK 发送：

```text
T_HC = inverse(T_WH) × T_WC
```

即完整的头显相对手柄位姿，不仅是位置差。矩阵为 4×4 齐次变换：左上 3×3 是相对旋转，右上 3×1 是以头显轴表达的相对位置，位置单位为米。

```text
T_HC = [ R_HC  p_HC ]
       [ 0 0 0   1  ]
```

来源：[OculusTeleop.cpp，构造与发送矩阵](https://github.com/rail-berkeley/oculus_reader/blob/main/app_source/Src/OculusTeleop.cpp#L1238-L1248)。当前本地只有 APK 和 Python 接收端，本次没有比对头显已安装 APK 与上游源码的二进制一致性；上述结论以已核对的 Reader 实现为依据。

本机 `oculus_reader.py` 接收 r/l 矩阵；`pub_pose.py` 再计算：

```text
T_published = adj_mat × T_received × r_adj × ros_to_arm_mat
```

当前配置的 `ros_to_arm_xyz` 为零，因此位置轴换算为 `(-z, -x, y)`；旋转另作固定修正，然后发布位置和四元数。固定换轴后仍是头显相对输入，并没有恢复成房间固定坐标。`frame_id=vr_device` 是消息标签，不提供额外的世界位姿信息。

仅有单只手柄的 `T_HC`，无法唯一恢复头显运动时的 `T_WC`；还缺少同一时刻的 `T_WH`。在 PC 端减去首次位置、改 frame_id 或设置一个固定 RPY，都不足以补回该信息。不过，如果另一只手柄固定并被有效追踪，可以用两手柄的相对变换消去共同头显变换，构造以固定手柄为原点的空间参考，详见替代方案 A。

## 2. 推荐实现：追踪空间输入 + 固定基座变换

固定点建议选机械臂基座原点，固定轴使用 URDF 的 `base_link`。若选桌角，则还要定义该点处的三轴方向，并标定桌角坐标系到基座的变换。一个点本身不能确定三维坐标轴。

完整链路：

```text
头显端的手柄追踪空间位姿 T_WC
        ↓ 左乘固定标定 T_BW
固定基座中的手柄位姿 T_BC
        ↓ 基座轴上的平移增量、独立的姿态增量
TCP 目标 → 原有 IK → 原有唯一 SDK 命令出口
```

### 头显端

现有 APK 的上游代码已经同时获得 `handPoseMatrix` 和 `headPoseMatrix`。最小改动是输出追踪空间中的 `handPoseMatrix`，而不输出 `headPoseMatrix.Inverted() * handPoseMatrix`。需要获取匹配版本的 APK 源码重新构建和安装；修改 Python 不能更改已编译 APK 的输出语义。

建议显式标记 `pose_frame=tracking_world`，并发送帧序号、SDK 位姿时间、追踪有效状态与参考空间标识，避免 PC 把两类矩阵静默混用。SDK 位姿可能针对预测时刻，时间字段应保留实际语义，不能将 PC 重发缓存的时刻当成新采样时刻。

另一种等价做法是同步输出 `T_WH` 与 `T_HC`，在 PC 用 `T_WC = T_WH × T_HC` 恢复。两个位姿必须基于相同追踪空间和时刻；对于现有源码，直接输出已经取得的 `T_WC` 更简单。

若另行采用 OpenXR 实现，使用 `LOCAL` 或支持的 `STAGE` 作为追踪参考，不能选随头部运动的 `VIEW`。`LOCAL/STAGE` 的原点也可能被重新定义，不能假定跨次启动永远是同一物理原点。[参考空间规范](https://registry.khronos.org/OpenXR/specs/1.0/man/html/XrReferenceSpaceType.html)

### 固定参考标定

求固定刚体变换：

```text
T_BW = [ R_BW  t_BW ]
       [ 0 0 0   1  ]

p_B = R_BW × p_W + t_BW
```

现场可在固定夹具上定义至少三个不共线的物理点，其机器人基座坐标已知。让手柄的同一个已知参考点依次定位到这些点，记录对应追踪坐标，使用刚体配准求旋转和平移，不拟合额外尺度。

不能把手柄外壳接触点直接当 SDK 追踪原点：若接触点相对手柄原点的偏移 `d_C` 已知，应先计算 `p_W_contact = p_WC + R_WC × d_C`。更稳妥的做法是使用明确几何位置与朝向的固定夹具。标定期间不需要让机器人跟随手柄。

验证旋转为右手正交旋转，检查各物理点的配准残差和各轴方向；不凭空规定精度阈值。若只做遥操平移增量，平移项 t 会相消，最小需求是固定方向旋转；若要输出相对于指定固定点的完整坐标，则同时标定 t。

保存原始点对、`T_BW`、单位、参考空间标识和标定日期。跨次会话使用前，在固定夹具上重新核验原点与方向。

### PC 端与遥操映射

PC 对追踪空间输入计算：

```text
T_BC = T_BW × T_WC
```

若确有手柄局部工具轴修正 K，则为 `T_BW × T_WC × K`，其定义必须明确。`T_BW` 已包含原始追踪轴到基座轴的旋转，不应再重复应用旧的 `adj_mat` 换轴；旧的右乘 `ros_to_arm_rpy` 也不能代替左乘世界到基座的变换。

世界坐标输入接通后，还要将平移增量与接入时的手腕/TCP 朝向解耦。每次 A/RG 捕获手柄基座位姿和 TCP 参考，单位缩放时计算：

```text
p_TCP_target(t) = p_TCP_reference + [p_BC(t) - p_BC(reference)]

R_TCP_target(t) = R_BC(t) × transpose(R_BC(reference)) × R_TCP_reference
```

这样，RG 重建的是增量零点，固定空间轴和 `R_BW` 不随转腕、头显移动或 RG 重按而变化。手柄在房间中沿同一方向移动，将始终对应同一基座方向；操作者转身不会重新定义固定坐标的“前方”。

现有 `calc_pose_incre(..., delta_frame="base")` 可以复用上述增量语义，前提是上游已经输出真正的基座坐标。仅将当前配置改成 `base`，仍不能去掉现有头显相对输入。也不能在只更改 APK 输出后保留完整的旧 TCP 共轭平移映射，否则握姿对平移方向的影响仍存在。

## 3. 改动位置与落地次序

| 层次 | 改动 |
| --- | --- |
| 头显 APK | 输出追踪空间位姿，明确空间、时刻与有效状态 |
| `ros_ws/src/oculus_reader/scripts/oculus_reader.py` | 解析新协议和状态，不将旧缓存冒充新帧 |
| `ros_ws/src/oculus_reader/scripts/pub_pose.py` | 加载固定标定，左乘 `T_BW`，发布正确 frame_id 与位姿时间 |
| `pub_delta_pose.py`、采集配置和 launch | 接入基座坐标增量语义，A/RG 重设零点而不重定义空间轴 |
| 数据记录 | 保存参考空间、固定变换及哈希，区分旧链路和新链路的数据语义 |

先完成 APK 与 PC 的只读位姿验证，再接入现有 IK 和 SDK 出口。保留原有运动限位、跟随开关和唯一命令出口。

## 4. 现场验收

1. 手柄固定在夹具上，移动、转动头显：固定坐标中的手柄位姿应基本不变，量化实际追踪噪声。
2. 手柄分别沿标定的 X/Y/Z 方向移动已知距离：输出方向与距离一致；改变初始握姿后重复，平移方向不应改变。
3. 松开 RG、转腕、重新按 RG：位置目标连续，重设零点不改变固定平移轴。
4. 再验证姿态转动的轴和正负方向，最后进行小幅现场遥操。
5. 参考空间重置、追踪无效或会话重启后，停止沿用旧变换驱动；先核验/重标固定参考，再重新接入。OpenXR 有专门的参考空间变更事件可供处理。[空间变更事件](https://registry.khronos.org/OpenXR/specs/1.1/man/html/XrEventDataReferenceSpaceChangePending.html)

该方案去掉头显作为随动数值参考的影响，仍依赖 Quest 的空间追踪能力，不承诺没有 SLAM 漂移。若要求跨天、重启后仍自动恢复同一物理原点，需要固定夹具重标，或另行设计可靠的物理标记/持久空间锚点重定位。
